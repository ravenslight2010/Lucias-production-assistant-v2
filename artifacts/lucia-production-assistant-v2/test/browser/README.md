# Authenticated browser regressions

## Dev-only visual importer preview

Open `/__visual-preview/imports` in the development preview to render the real
workbook-review component with a synthetic three-product workbook. The route is
available only in Vite development mode, runs outside Clerk/session bootstrap,
contains no facility data, and disables file selection and every save action.
Use it for screenshot and responsive-layout checks; it does not replace the
authenticated browser regressions below.

## Profile snapshot regression

`profile_snapshots.py` runs the real UI against the real development API, with
real XLSX files generated by the app's installed XLSX dependency. No API or
authentication responses are mocked.

Use a **disposable development facility**, never production or an operator's
facility. The test creates uniquely named profiles and one planned run, and
keeps them for inspection. It never deletes existing data. Sign in using Clerk
as a facility owner or manager and save a short-lived Playwright storage state
outside Git (for example under `generated-artifacts/`). Do not commit that file
or browser traces: they can contain session credentials and workbook data.

From a Python environment with Playwright and Chromium available:

```sh
E2E_ALLOW_SYNTHETIC_WRITES=1 python artifacts/lucia-production-assistant-v2/test/browser/profile_snapshots.py \
  --base-url "https://YOUR-DEVELOPMENT-HOST" \
  --storage-state generated-artifacts/auth.json
```

Alternatively, an authenticated browser harness can import
`run_journey(page, base_url)` directly. This supports Replit's programmatic Clerk
test login without adding an authentication bypass to the application.

Coverage:
- Import original workbook, create planned run, compare complete captured data.
- Add a second workbook revision and rename both brand and flavor.
- Cancel, then explicitly confirm a merge; check both bundles survive and source
  disappears from the active cards and run selectors without manually refreshing.
- After every mutation stage, directly load and reload the run URL; compare
  captured brand, flavor, revision, and the entire workbook payload.
- A competing authenticated device wins an edit while a stale form remains open.
  Refresh the list in the stale tab before saving, require HTTP 409, and verify
  the winning name and revision survive reload. Reopening rename loads fresh data.

Two isolated browser contexts share a test identity to model simultaneous facility
devices; revision protection is independent of actor identity. Cookie jars must
be isolated because each device bootstraps its own CSRF-bound API session.
The harness may use separate authenticated facility-member identities for the
competing edit if needed.

## Schedule import regression

`schedule-import.mjs` exports `verifyScheduleImport(page, baseURL)`, accepting a
real Playwright Page already signed in through Clerk as a **fresh synthetic user
with no facility**. Use the development database only. It creates an isolated
synthetic facility and two active profiles through the UI; it never changes an
existing facility, bypasses authentication, intercepts API responses, or starts
production runs.

Run both managed API/web workflows, sign in programmatically with the authenticated
browser testing harness (override Clerk login claims), then invoke:

```js
const { verifyScheduleImport } = await import('./schedule-import.mjs');
const result = await verifyScheduleImport(page, previewURL);
```

`page` can come from any Playwright harness. Authentication must be established
before invocation; do not commit cookies, tokens, storage state, or credentials.
No separate Playwright dependency or browser installation is required by this
module; use the harness's browser.

For a Playwright notebook that supplies `page`, `fs`, `Buffer` and `crypto` but
cannot import ESM, bundle the **same scenario** from the workspace root using the
API package's existing esbuild installation:

```sh
artifacts/api-server/node_modules/.bin/esbuild \
  artifacts/lucia-production-assistant-v2/test/browser/schedule-import.mjs \
  --bundle --platform=browser --format=iife --global-name=ScheduleImportRegression \
  --outfile=generated-artifacts/schedule-import.js
```

In the authenticated notebook:

```js
eval(fs.readFileSync('/home/runner/workspace/generated-artifacts/schedule-import.js', 'utf8')
  + '\nglobalThis.scheduleImportRegression = ScheduleImportRegression;');
const result = await globalThis.scheduleImportRegression.verifyScheduleImport(page, previewURL);
```

The generated bundle is ignored by Git and publishing. It contains the real XLSX
library and scenario, not a replacement set of manual steps.

If a scenario assertion stops **after** the first import, the existing synthetic
facility can be used to verify only the remaining detail/replay/reload checks:

```js
await globalThis.scheduleImportRegression.verifyScheduleImport(page, previewURL, {
  suffix: '<suffix from this scenario-created facility>',
  today: '<original browser-local import date>',
});
```

This guarded checkpoint requires the matching synthetic facility name, two
profiles, and exactly one schedule batch with the generated filename. It does
not replace a full fresh-account run; it avoids repeating already-passed setup
when confirming a test assertion fix. Omit the third argument for normal runs.

The scenario generates real XLSX bytes relative to the browser's local date.
It checks a past-only product is excluded, today is retained, all three eligible
rows and their notes/source coordinates are reviewed without writes, exact product
matches are selected automatically, an alias blocks import until explicitly mapped,
and all planned runs retain the selected profile snapshots. It checks run-list
and detail UI plus authenticated API data, recent import history, identical-file
re-upload, unchanged run IDs and contents, and persistence after reload.

Synthetic data is intentionally retained as evidence in its isolated facility.
Do not delete unrelated data to reset a test; use another fresh account.
The fixture/parser contract also runs without a browser via the package's `test`
script. This is separate from the product-workbook/manual run-control smoke test.
